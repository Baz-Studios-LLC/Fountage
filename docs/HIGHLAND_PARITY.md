# Highland parity: release requirements

Baseline: Highland Pro for macOS, audited October 14, 2026. Preserve compatibility with Highland 2 documents as well. User priorities: native Mac experience, exceptional visual quality, and full Highland feature parity. These are release gates, not optional polish. The revised cross-platform direction in `docs/GOAL.md` targets Slint/Rust on macOS, Windows and Linux; verify each platform independently. An iOS app is outside scope; Mac document sync and review-sharing workflows remain in the audit.

This is an initial inventory, not a claim of exhaustive coverage. Expand it through the installed app's menus, settings, templates, help, and representative documents. An item is complete only when its behavior and data persistence have been tested. Do not count a placeholder button, an approximate implementation, or a roadmap entry as parity.

## Current foundation

The SwiftUI/AppKit document app under `macOS/` remains the working reference and fallback. Slint/Rust migration is active under `prototypes/slint/`, following the user’s revised direction in `docs/GOAL.md`. Track its verified workflows separately: a Swift feature listed below does not establish Slint support. Rust owns shared document operations and analysis; the Swift interface also uses a C ABI. The previous Iced experiment is retained behind the `ice-prototype` Cargo feature for comparison. No Highland feature is yet certified at parity.

## Highland file compatibility

Source C: [Published Highland format description](https://quoteunquoteapps.com/highland-pro/highland-format).

Highland documents are ZIP-compressed customized TextBundles containing primary text, JSON metadata, assets, and potentially additional subdirectories. The publisher warns that these extra contents matter to revisions and other metadata. The public description is not a complete specification.

Compatibility gates:

1. Read supported containers without writing to the original document.
2. Reject unsafe archive paths and oversized decompression before extraction.
3. Preserve primary text exactly; report encoding failures clearly.
4. Inventory and retain unknown entries rather than silently dropping them.
5. Test title pages, images, revisions, snippets, highlights and metadata individually.
6. Keep imported copies separate until round-trip fidelity is proven.
7. Use a copy of the user's Reflected screenplay as an explicit real-world fixture when implementing this adapter; do not modify the source.

## Fountage additions beyond Highland parity

### MCP server — planned

User-requested: let people connect their own AI through Model Context Protocol to help control Fountage. Support compatible MCP clients without requiring a particular AI provider or a bundled AI subscription.

- Expose document context, selected text, outline, notes and available app commands through a documented MCP interface.
- Provide structured tools for navigating, editing, organizing and saving documents through the same application operations used by the native UI.
- Make connections opt-in, with clear document access and read/edit permissions, visible connection status and a disconnect control.
- Keep AI edits undoable and reject stale edits; preserve unsaved work, manuscript text, metadata and assets. Require explicit authorization for destructive operations.
- Provide setup instructions and examples for connecting an external AI client. Explain that any content read by that client follows the user's chosen client's data handling.

Acceptance: connect compatible clients, inspect a selected document, perform and undo an edit, navigate its outline, save/reopen without data loss, reject unauthorized or stale edits, and verify that disconnect revokes access. Research the current MCP specification before implementation. This is a planned Fountage capability, not an existing feature or a Highland parity claim.
